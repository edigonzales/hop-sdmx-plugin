[[sdmx-input]]
= SDMX Input
:plugin-id: SdmxInput
:plugin-type: transform
:description: Read SDMX observations using dynamic metadata discovery and a saved output schema.

== Description

SDMX Input discovers a dataflow's Data Structure Definition (DSD), codelists and content constraints.
The author explicitly loads and saves the structure. At runtime the transform validates the current
structure against the saved schema before emitting observations. Codes and labels may change without
changing the schema. Component identifiers, roles, dimension order and data types must remain compatible.
A version identifies a structural definition; it does not freeze the observation values.

BFS Swiss Stats Explorer is the verified provider. The endpoint is configurable, but other providers
must support REST v1, SDMX-JSON structure 1.0 and SDMX-CSV data 2. Those three versions are independent.

== Input

This is a source transform. Do not connect incoming rows and use exactly one copy.
All source and filter text values support Hop variables such as `${START_PERIOD}`. Variable expressions
are stored verbatim; neither schema discovery nor preview replaces them with the resolved value.
Pipeline parameters must be activated before pipeline preparation, as Application Launcher already does.

The Dimensions tab shows one row per non-time dimension, in DSD order: its identifier and name,
an editable filter expression and a *Choose...* button. Code selections use projected content
constraints, not an interactive availability service. Even valid codes may produce no observations.
Uncoded dimensions remain editable. A missing codelist reference is an error rather than guessed metadata.

The Output fields tab shows name, component, Hop type and whether the field contains a label.
`getFields()` reads only these saved fields and performs no HTTP calls. Changing period or filter values
cannot change the output schema. Changing the dataflow is allowed only if its structure is compatible.

=== Preview window

Preview uses the same structure validation, query and observation reader as execution, stopping after
50 observations. The server may still prepare the full requested selection; use a narrow period.
Closing the main dialog cancels its pending HTTP operation. Cancel request leaves the draft editable.

[[output]]
== Output

One row per observation, including dimensions, time, measures and attributes. Codes and time periods
are strings. Uncoded decimal/integer measures use Hop BigNumber; float/double measures use Number.
Missing values become null, not zero. Unknown label codes fall back to the code. Labels use the requested
language, its base language, then English, then the code. They never become field names.

Data requests use `labels=id`. For BFS, `labels=both` combines code and text within cells and headers;
this plugin instead resolves label columns from the structure. Codelists are refreshed at execution.

Unit, multiplier, decimals and observation-status attributes are preserved. For example, `397.708`
with `MULT=6` means millions of the reported unit. No automatic scaling, aggregation, pivoting or
semantic interpretation is performed. CSV control fields are validated and not exposed as user columns.

== Supported engines

Local Hop pipeline engine on Hop 2.19.0, Java 21/25. Beam and remote/distributed engines are not verified.

== Examples

See link:../../examples/bfs-health-financing/README.md[BFS health financing example]
and download link:../../examples/bfs-health-financing/bfs-health-financing.hpl[the pipeline].
It includes `START_PERIOD`, `END_PERIOD`, `FINANCING_SOURCES`, `SDMX_ENDPOINT` and `OUTPUT_FILE` parameters.
Defaults select one source and year; edit the parameters without changing the schema.

Application Launcher needs no extension: expose `START_PERIOD` and `END_PERIOD` as string parameters
in the application sidecar; its activated Hop parameters resolve the transform's expressions.
Keep the pipeline's saved structure and downstream field mappings fixed. Multiple values can be supplied
as a comma-separated string, e.g. `Q_1,Q_2`.

[[error-handling]]
== Error handling

Structure mismatches fail before the first output row. CSV content is checked while streaming; a malformed
later record fails the pipeline after earlier rows may have been emitted. Use staging and publish outputs
only after a successful run if downstream writes must be atomic.

Connect/read timeouts are 30 seconds. HTTP 429/502/503/504 and connect/read timeouts before opening the
response body receive at most two retries. A stream is never replayed after output starts. Authentication,
redirects, unsupported response formats and missing datasets produce explicit errors. No-data HTTP 204
is reported as an error; a valid CSV header without rows produces zero rows. Stop closes the connection;
platform network cancellation may take up to the configured timeout.

[[limitations]]
== Limitations

* Full snapshots only: no `updatedAfter`, watermark or merge implementation.
* Only insert/replace observation rows (`I`/`R`) are accepted. Delete actions, incomplete dimension keys,
  attribute-only rows and non-finite numbers fail explicitly.
* Constraints are projected to per-dimension choices. They do not imply that all selected combinations exist.
* Fixed schemas require explicit refresh after incompatible server changes. There is no generic JSON-row mode.
* No authentication configuration or provider-specific adapters in this first version.
* Structure/catalog responses are bounded at 16 MiB; data is streamed.

== Development

Core code is independent of Hop/SWT. The transform stores schema and field mappings as JSON inside
Hop metadata properties. Standard metadata XML serialization preserves variable expressions.
The repository uses `hop-plugin-ci`, its common Maven parent and the `standard-plugin` contract.
Run `scripts/build-and-install.sh` to verify and install in a local Hop directory; default is
`/Users/stefan/Downloads/hop`. Automated installed tests use a disposable installation.
